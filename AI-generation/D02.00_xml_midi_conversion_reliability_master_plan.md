# D02.00 XML/MIDI Conversion Reliability Master Plan

Document Status: Draft v0.1  
Date: 2026-07-30  
Role in Program: Parent research document for conversion reliability across the music-transformer toolchain

## 1. Purpose
This document defines the parent reliability program for XML/MIDI conversion and cleanup tooling used in the compositional workflow.

The objective is to establish repeatable validation, failure classification, and incremental hardening for current scripts before broader automation is expanded.

## 2. Tool Scope
This research stream currently covers the following executable tools.

1. music-transformer/cleanup_midi_notes.py
2. music-transformer/enforce_piano_strict.py
3. music-transformer/convert_midi_to_grandstaff_xml.py
4. music-transformer/main.py and supporting src modules where cross-format transformations occur

## 3. Problem Context
Current scripts provide useful transformations, but behavior can vary across real-world files with dense controllers, overlapping events, tempo changes, and notation-performance mismatches.

Reliability work is therefore framed as a formal test and regression effort, not ad hoc debugging.

## 4. Program Structure
This parent document governs three initial child studies.

1. D02.01 cleanup MIDI notes validation pilot
2. D02.02 MIDI-to-Grandstaff MusicXML conversion accuracy pilot
3. D02.03 strict piano rule regression suite

Each child defines:

1. fixed corpus
2. expected outcomes
3. failure taxonomy
4. acceptance thresholds
5. change log and retest rule

## 5. Research Questions
This stream asks the following.

1. Which input conditions produce unstable or incorrect outputs in each tool?
2. Which failures are data-specific versus algorithmic?
3. What minimum test coverage is required before tool changes are considered safe?
4. How can reliability be improved without breaking current successful cases?

## 6. Shared Reliability Criteria
All child studies use common quality gates.

1. Deterministic output for identical input and settings.
2. No silent corruption of timing, note pairing, or measure intent.
3. No unhandled exceptions on in-scope files.
4. Explicit reporting or logging when assumptions are violated.
5. Re-test pass on previously failing files after a fix.

## 7. Common Test Artifact Policy
All child studies should preserve:

1. input test files
2. output artifacts
3. tool version/hash or commit reference
4. run command and parameters
5. observed vs expected behavior

Store findings in markdown logs and keep small representative assets in-repo where practical.

## 8. Failure Taxonomy
Use these categories for consistent triage.

1. Parse/load failure
2. Timing drift or offset error
3. Note pairing error (dangling note-on/off)
4. Musical structure error (phrase/measure misalignment)
5. Over-pruning or under-pruning
6. Controller/meta event loss
7. Non-deterministic behavior
8. Performance failure (excessive runtime or memory)

## 9. Sequence and Dependencies
Run child studies in this order.

1. D02.01 first, to stabilize note-event correctness.
2. D02.02 second, to validate notation conversion after cleanup assumptions are known.
3. D02.03 third, to formalize idiomatic strict-piano constraints with regression protection.

## 10. Deliverables
The D02 stream is complete when the following exist.

1. three completed child reports with pass/fail summaries
2. consolidated defect list prioritized by severity and frequency
3. proposed code-change plan linked to failing cases
4. regression checklist for future releases

## 11. Exit Criteria
D02.00 moves to maintenance mode when:

1. child pilots are completed and reproducible
2. critical failures have either fixes or documented constraints
3. baseline regression corpus is defined and runnable

## 12. Relationship to Other Streams
This stream supports D01 by improving fidelity and predictability of symbolic artifacts that may enter AI-generation experiments.
